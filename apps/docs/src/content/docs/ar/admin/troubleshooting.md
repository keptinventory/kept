كل إدخال هو عرض، وسببه، والإصلاح. تفترض الأوامر Docker Compose؛ وبالنسبة لـ Helm تنطبق نفس الفحوصات على الـ pods.

## أولاً، انظر

- **الإدارة → الحالة** تسمي معظم المشاكل بنفسها: البريد، مهام الخلفية الفاشلة، فحص التذكير، النسخ الاحتياطية وتدريب الاستعادة، الأقراص، الإصدار وهجراته، HTTPS.
- **السجلات:** `docker compose logs kept` و `docker compose logs migrate`. `KEPT_LOG_FORMAT=pretty` يجعلها قابلة للقراءة بالعين؛ `KEPT_LOG_LEVEL` (الافتراضي `info`) يحدد المستوى.
- **معرف طلب:** كل استجابة تحمل `x-request-id`؛ ابحث في السجل عنه لتجد السطر الذي ينتمي إلى تقرير.
- **الفحوصات (Probes):** `/healthz` (العملية تخدم HTTP)، `/readyz` (كلا اتصالا قاعدة البيانات يستجيبان)، `/version` (الإصدار، الالتزام، المصدر). انظر [المراقبة](/ar/admin/observability/).
- **فحوصات يمكنك تشغيلها:** `kept admin backup verify`، `kept admin storage verify --store local` (أو `s3`) و `kept admin config` ([واجهة سطر الأوامر](/ar/admin/cli/)).

## `docker compose up` يتوقف عند خدمة `bootstrap`

**السبب:** خدمة `bootstrap` أحادية التشغيل (`kept bootstrap`) لم تستطع إعداد تسجيلات دخول قاعدة البيانات. سجلها يوضح السبب: `docker compose logs bootstrap`. الأسباب الشائعة: الصورة أقدم من 1.13.0 ولا تحتوي على أمر `bootstrap` (اضبط `KEPT_IMAGE` على 1.13.0 أو أحدث)؛ أو تم إعداد الحلقة المحلية (loopback) لقاعدة البيانات لتتطلب كلمة مرور، و `KEPT_DB_SUPERUSER_PASSWORD` في `.env` لا تحتفظ بها.

**الإصلاح:** صحح ما يذكره السطر وشغّل `docker compose up -d` مرة أخرى؛ الـ bootstrap آمن للتشغيل أي عدد من المرات.

## Kept يخرج عند البدء مع `kept: invalid environment: …` أو سطر `kept:` آخر

**السبب:** يتم فحص البيئة قبل بدء أي شيء، والمشكلة الأولى تتوقف عندها العملية بسطر واحد يسميها. الشائعة منها:

| السطر يقول | الإصلاح |
|---|---|
| `kept: invalid environment: KEPT_PUBLIC_URL` | اضبط العنوان: `docker compose run --rm init` ([التثبيت](/ar/install/compose/#١-اكتب-ملف-env)) |
| `KEPT_DATABASE_URL has no password, and KEPT_DB_APP_PASSWORD_FILE: … does not exist` | الـ bootstrap لم يشغل: ابدأ بـ `docker compose up -d`، الذي يشغله أولاً، وليس `docker compose up kept` وحدها |
| `KEPT_SECRET_KEY and KEPT_AUTH_SECRET are set together or not at all` | اضبط كلاهما، أو ألغِ كلاهما لاستخدام الزوج المولَّد في وحدة تخزين الإعدادات |
| `<path>/secrets.json exists but …; fix or restore it` | ملف المفاتيح المولَّد تالف: أعد المفاتيح من [مجموعة الاسترداد](/ar/admin/recovery-kit/) |
| `KEPT_BACKUP_DIR is inside KEPT_DATA_DIR …` | وجّه النسخ الاحتياطي لقرص آخر |
| `a backup target is set, and the nightly backup dumps the database as kept_owner …` | أعطِ العامل `KEPT_OWNER_DATABASE_URL` ([النسخ الاحتياطية](/ar/admin/backups/#التفعيل)) |
| `set one backup target, not …` | احتفظ بواحد من `KEPT_BACKUP_DIR`، `KEPT_BACKUP_S3_BUCKET`، `KEPT_BACKUP_SFTP` |
| `KEPT_STORAGE=s3 needs …` | أضف إعدادات S3 التي يسميها ([التخزين](/ar/admin/storage/)) |
| `KEPT_OIDC_ISSUER is set without KEPT_OIDC_CLIENT_ID` | أضف معرّف العميل، أو ألغِ المُصدِر (issuer) |

كل متغير موجود في [مرجع الإعدادات](/ar/reference/configuration/).

## غُيّرت كلمة مرور قاعدة البيانات في `.env`، والآن لا شيء يتصل

**السبب:** مع `compose.yaml` الخاص بـ Kept 1.13.0 يصلح هذا نفسه: الـ bootstrap يضبط كلمة مرور كل تسجيل دخول إلى القيمة الموجودة في `.env` (أو ملفها) في كل `docker compose up -d`. يحدث هذا مع `compose.yaml` أقدم، الذي كان يضبط كلمات المرور مرة واحدة، عند إنشاء وحدة تخزين `kept-db` لأول مرة.

**الإصلاح:** استخدم `compose.yaml` الحالي وشغّل `docker compose up -d`. مع القديم، غيّر كلمة مرور الدور في Postgres لتطابق، ثم أعد التشغيل:

```sh
docker compose exec db psql -U postgres -c "ALTER ROLE kept_app PASSWORD '<the new password>'"
```

(الدور هو `kept_owner`، `kept_app`، `kept_auth` أو `kept_system`، مطابِق للمتغير.)

## `/readyz` تجيب 503

**السبب:** أحد اتصالي الويب بقاعدة البيانات (`app` و `system`، يظهران كـ `false` في جسم الاستجابة) لا يستطيع تشغيل استعلام. السجل يحمل `readiness check failed`. عند البدء، ينتظر Kept حوالي دقيقتين لقاعدة بيانات لا تزال تبدأ قبل أن يستسلم.

**الإصلاح:** تحقق أن `docker compose ps db` سليم، وأن تسجيل الدخول المسمى `false` له كلمة المرور الصحيحة (أعلاه). في Postgres المُدار، تحقق أن تسجيلات الدخول الأربعة موجودة ([Postgres المُدار](/ar/install/managed-postgres/#تسجيلات-الدخول-الأربع)).

## "This Kept is set up for …" أو "The request did not come from this site."

- **التطبيق:** "This Kept is set up for *address*. Open it there."، في صفحة تسجيل الدخول أو كشريط فوق التطبيق عند رفض الحفظ.
- **واجهة البرمجة (API):** 403، "The request did not come from this site."

**السبب:** عملية كتابة تحمل كوكي Kept يجب أن تأتي من المنشأ (origin) الدقيق لـ `KEPT_PUBLIC_URL`، أو أحد `KEPT_EXTRA_ADDRESSES`: المخطط، المضيف والمنفذ. Kept يقارنه مع رأس `Origin` في المتصفح، وهو العنوان في شريط العناوين؛ وكيل عكسي (reverse proxy) بينهما لا يغيّر شيئاً. فتح Kept بعنوان آخر (عنوان IP بدل الاسم، `http` بدل `https`، منفذ مختلف، عنوان الوكيل الداخلي) يجعل كل كتابة 403. الروابط، رموز QR ورسائل الدعوة تُبنى من نفس القيمة، ومفاتيح المرور (passkeys) تُسجّل لاسم مضيفها.

**الإصلاح:** اضبط `KEPT_PUBLIC_URL` على ما يظهره شريط عناوين المتصفح بالضبط، أعد التشغيل، وافتح Kept دائماً هناك. إذا كنت تصل Kept بعنوانين حقيقيين، مثل اسم شبكة محلية (LAN) واسم Tailscale، اذكر الباقي في `KEPT_EXTRA_ADDRESSES` ([أكثر من عنوان واحد](/ar/install/home-network/#أكثر-من-عنوان-واحد)).

## Kept لا يبدأ بعد ترقية، و `migrate` خرج بخطأ

**السبب:** خدمة `kept` تبدأ فقط بعد نجاح `migrate`. قبل ترقية قاعدة بيانات بها بيانات، `kept migrate` يأخذ نسخة قبل الترقية عند ضبط هدف نسخ احتياطي؛ **إذا فشل التقاط النسخة، لا تتم أي ترقية** ويخرج مع السبب ([الترقيات](/ar/admin/upgrades/#النسخة-الاحتياطية-قبل-كل-ترقية)).

**الإصلاح:** اقرأ `docker compose logs migrate`، أصلح النسخ الاحتياطي (الهدف، كلمة المرور، التحميل على `migrate`)، وشغّل `docker compose up -d` مرة أخرى. للترقية دون التقاط نسخة عمداً، اضبط `KEPT_UPGRADE_SNAPSHOT=off` لتلك العملية.

## Kept يرفض البدء مع `downgrade_refused`

**السبب:** الصورة أقدم بأكثر من إصدار واحد من قاعدة البيانات (أو أن قاعدة البيانات لديها هجرات لم يسجلها أي إصدار). يُسمح بإصدار واحد للخلف فقط؛ أكثر ليس مسموحاً.

**الإصلاح:** شغّل الإصدار الأحدث مرة أخرى، أو [استعد](/ar/admin/restore/) النسخة قبل الترقية التي أخذها الإصدار الأقدم. `KEPT_ALLOW_DOWNGRADE=1` يفرض البدء ويُدوّن؛ استخدمه فقط عندما تقول ملاحظات الإصدار بذلك ([العودة إصدار واحد](/ar/admin/upgrades/#الرجوع-لإصدار-سابق-واحد)).

## رمز الإعداد ضائع، أو الإعداد مقفل

**السبب:** الرمز يُطبع مرة واحدة، بواسطة العملية التي خلقته. الرموز الخاطئة تُقفل العنوان الذي أرسلها، والعديد من الرموز الخاطئة يُقفلون المثيل (instance).

**الإصلاح:** `docker compose run --rm migrate admin setup-code` يصدر رمزاً جديداً ويرفع القفل على مستوى المثيل؛ القفل على مستوى عنوان ينتهي من تلقاء نفسه. إذا كان الجميع مقفلين في وقت واحد، اقرأ الإدخال التالي.

## الجميع يواجهون نفس حدود تسجيل الدخول

**السبب:** خلف وكيل عكسي Kept يرى عنوان الوكيل لكل زائر ما لم يكن الوكيل في `KEPT_TRUSTED_PROXIES`، لذا الجميع يشتركون في مجموعة حدود واحدة.

**الإصلاح:** اذكر عنوان الوكيل كما يراه Kept في `KEPT_TRUSTED_PROXIES` ([الوكلاء العكسيون](/ar/install/reverse-proxy/#ثق-بالوكيل-والوكيل-فقط)).

## الرفع يفشل، أو الصور الكبيرة لا تصل أبداً

**السبب:** Kept يرفض ملفاً أكبر من `KEPT_MAX_FILE_MB` (25 ميغابايت افتراضياً) مع 413. وكيل أمامه غالباً له حد جسم أصغر خاص به ويفشل أولاً.

**الإصلاح:** ارفع حد الوكيل إلى `KEPT_MAX_FILE_MB` على الأقل ([السماح بالمرور للرفع](/ar/install/reverse-proxy/#دع-الرفع-يمر)).

## الكاميرا، التثبيت، الإشعارات (push) أو الموقع لا تعمل على الهواتف

**السبب:** الهواتف تسمح بها فقط على منشأ آمن (secure origin)؛ عنوان شبكة محلية (LAN) عبر HTTP عادي ليس كذلك. عبر HTTP يرفض Kept أيضاً إظهار القيم السرية، التصديرات، رموز الدخول (access tokens)، اتصالات OAuth، تنزيل مجموعة الاسترداد وإعدادات النسخ الاحتياطي.

**الإصلاح:** [ضع Kept على HTTPS](/ar/install/https/) واضبط `KEPT_PUBLIC_URL` على عنوان `https://`.

## حفظ مقدّم ذكاء اصطناعي (AI provider) أو ويب هوك (webhook) يفشل: "That address is on a private network."

**السبب:** الطلبات الصادرة تُرفض إلى عناوين خاصة، حلقة محلية (loopback) ومحجوزة (`private_address`). مقدّم على شبكتك الخاصة، بما في ذلك `http://ollama:11434/v1` الخاص بـ Compose، يُحل إلى واحد منها.

**الإصلاح:** مشرف مثيل يفعّل **الإدارة → الإعدادات → السماح بالعناوين الخاصة**. انظر [نموذج الأمان](/ar/admin/security-model/#طلبات-صادرة-ssrf).

## لا يصل بريد

**السبب:** بدون `KEPT_SMTP_URL` و `KEPT_SMTP_FROM`، البريد يُسجّل فقط كمستحق، والإدارة → الحالة تقول إن البريد غير مضبوط.

**الإصلاح:** اضبط كلاهما وأعد التشغيل ([التثبيت](/ar/install/compose/#٥-بعد-ذلك)).

## النسخ الاحتياطية لا تشغّل، أو تنبيه "Backup stale" يُطلق

**السبب:** عادةً أحد: لا هدف أو لا كلمة مرور (لا يوجد نسخ احتياطي غير مشفّر)، العامل بدون `KEPT_OWNER_DATABASE_URL`، هدف دليل غير محمّل على الحاوية، أو هدف غير مملوك لمستخدم Kept (uid 10001).

**الإصلاح:** اتبع [النسخ الاحتياطية](/ar/admin/backups/#التفعيل)، ثم شغّل واحدة يدوياً واقرأ ماذا تقول:

```sh
docker compose run --rm --no-deps --entrypoint kept kept admin backup
```

تخرج بـ 1 عند تحذير، بالاسم:

| التحذير | المعنى، وماذا تفعل |
|---|---|
| `backup_suspicious_size` | أصغر بكثير من آخر نسخة صالحة؛ إذا كان الانكماش حقيقياً، `kept admin backup --accept-size` |
| `files_unreadable` | restic لم يستطع قراءة بعض الملفات؛ تحقق أذونات وحدة تخزين البيانات |
| `blob_checksum_mismatch` | ملف مخزّن لم يعد يطابق SHA-256 الخاص به؛ تحقق القرص |
| `readable_incomplete` | نسخة قابلة للقراءة لموقع فشلت؛ السجل يسميها |

بعد تعطل، قفل restic قديم يمكن أن يحجب كل عملية: `kept admin backup unlock` يزيله (يرفض أثناء تشغيل نسخ احتياطي).

## استعادة ترفض البدء

**السبب:** Kept يستعيد فقط في قاعدة بيانات **فارغة**، ويتحقق أن `pg_restore` يطابق إصدار Postgres الرئيسي للخادم وأن الامتدادات (extensions) موجودة.

**الإصلاح:** أنشئ قاعدة بيانات فارغة جديدة مع الامتدادات، كما في [الاستعادة](/ar/admin/restore/#الاستعادة); لا توجّه الاستعادة أبداً للقاعدة الحية.

## بعد استعادة، القيم السرية ومفاتيح الذكاء الاصطناعي لا يمكن قراءتها

**السبب:** هي مختومة بـ `KEPT_SECRET_KEY`، الذي ليس في النسخة الاحتياطية.

**الإصلاح:** ضع مفاتيح مجموعة الاسترداد في `.env` (مع `KEPT_SECRET_KEY_VERSION` و `KEPT_SECRET_KEYS_RETIRED` إذا وردت) وأعد التشغيل. إذا كانت المجموعة تذكر مفاتيح متقاعدة، شغّل `kept admin rotate-key --resume` بمجرد تشغيل Kept. بدون المفتاح تلك القيم ذهبت للأبد.

## `kept admin` يقول `KEPT_OWNER_DATABASE_URL … is required`

**السبب:** معظم أوامر الإدارة تحتاج تسجيل دخول مالك قاعدة البيانات، الذي تملكه خدمة `migrate` فقط.

**الإصلاح:** شغّلها كـ `docker compose run --rm migrate admin <command>`، أو لـ `rotate-key`، `backup`، `restore` و `export`، أعطِ خدمة `kept` تسجيل دخول المالك في `compose.override.yaml` ([واجهة سطر الأوامر](/ar/admin/cli/#التشغيل-تحت-compose)).

## حاوية عامل فقط (worker-only) غير سليمة (unhealthy)

**السبب:** مع `KEPT_ROLE=worker` فحص الصحة يقرأ الملف الذي تلمسه حلقة المهام (`/tmp/kept-worker-alive`)؛ يفشل عندما الحلقة لم تستعلم قاعدة البيانات لمدة دقيقتين.

**الإصلاح:** تحقق سجل العامل واتصاله بقاعدة البيانات؛ نفس فحوصات قاعدة البيانات الخاصة بـ `/readyz` تنطبق.

## لا يزال عالقاً

افتح قضية مع الإصدار من `/version`، كيف يشغّل Kept، وأسطر السجل ذات الصلة مع إزالة أي شيء خاص. مشكلة أمنية تمر عبر الإبلاغ الخاص عن الثغرات ([نموذج الأمان](/ar/admin/security-model/#الإبلاغ-عن-ثغرة)).
